# 非 Coding Windows 工具准确度修复方案

> 更新日期：2026-10-15  
> 版本：v9。只保留独立模型检查；检查间隔可配置，默认每完成 5 轮工具执行检查一次。  
> 当前状态：已实施。第 14 节说明唯一检查流程，第 15 节说明模型与 Scroll，第 16 节说明临时引导，第 17 节说明配置、删除范围与验证。  
> 核心要求：只分析当前任务的工具调用和结果；保留原有权限、限制判定和并行方式；引导是否采纳由主模型根据实际情况决定。

## 1. 先说明这次要做什么

这次不重新设计工具系统。修改分为两部分：先澄清已有说明，再增加独立的失败纠正模块。

第一部分已做两件事：

1. 在 Windows 非 Coding 模式的现有提示词中，用少量文字提醒模型正确使用当前 Shell、工作目录和目标路径。
2. 工具已经报错或拦截调用时，把原因和正确的下一步解释清楚，减少模型原样重试或改错目标。

少数通用异常消息可以补充一句恢复建议，但不是为了凑齐数量而全部修改。

第二部分是 FailureLoopGate：记录当前任务的工具调用和实际结果，累计达到配置轮数后，在工具完成后、下一次 ReAct 推理前，使用同一模型进行独立检查。默认间隔为 5 轮。只在发现重复执行、相似执行或循环时，向下一次推理临时加入可自行决定是否采纳的引导。检查记录单独使用 Scroll，详见第 14 至 17 节。

### 1.1 对几个关键问题的直接回答

| 用户关心的问题 | 本版决定 |
|---|---|
| 会修改之前的限制逻辑吗？ | 不修改。原来允许和禁止的操作保持一致。 |
| 会修改之前的并行逻辑吗？ | 不修改。并行说明、调用顺序要求和实际调度均保留。 |
| 会增加 Windows 非 Coding 的提示词吗？ | 可能补充一小段，优先利用原有位置，不新增一套长篇规则。 |
| 会影响 Coding 或其他系统吗？ | 新增或替换的说明只在 Windows 非 Coding 请求中出现，其他模式文字与行为保持原样。 |
| 会增加失败检测门或后台判断吗？ | 增加 FailureLoopGate；工具完成后，等待同一模型的独立检查，再进入下一次主推理，不另起后台判断任务。 |
| 修改面有多大？ | 原文字修改仍限于 utils.py 与 shell.py；检查分为配置、工具记录收集、独立模型分析和临时引导，其余位置只做必要接线。 |
| 能保证模型行为完全不变吗？ | 不能。文字更清楚本来就是为了影响模型选择，但原有规则的含义、优先级和代码判定必须保持不变。 |

### 1.2 “精简”具体指什么

不是把必要规则删掉，而是：

- 同一个要求已经写清楚，就不再换几种说法重复添加。
- 保留原有流程，只澄清模型容易理解错的地方。
- 已有正确的工具说明不整体重写。
- 不增加新工具、另一套权限判断或后台监控；失败纠正的配置和模型检查独立放置。
- 不把其他已发现的代码问题一起塞进本次修改。

本次可以减少部分误用和无效重试，但不承诺解决所有准确度问题。

## 3. 为什么只改这两类说明

### 3.1 模型现在已经能看到哪些信息

当前模型并不是只看一段总提示词。与这次任务相关的说明主要来自：

1. 工作区提示文件：规定总体流程、Skill 使用和操作边界。
2. 环境信息：说明 Windows、Coding 与否、默认 Shell、默认工作目录和挂载目录。
3. 工具使用说明：告诉模型该选哪个工具、怎样填写参数。
4. 工具注册后实际给模型的描述：包括函数说明，以及包装工具时追加的规则。
5. 工具返回的错误消息：告诉模型刚才为什么失败。

同一要求可能在几个位置出现。如果不同位置说法不一致，模型就容易反复尝试。

这次的目标是让这些说明相互配合，不是再增加一套覆盖它们的新规则。

### 3.2 现有并行说明已经存在

目前 shell_policy.py 中有两段共享说明：

- WINDOWS_NON_CODING_SHELL_GUIDANCE：说明原子命令、cwd、进程状态和单任务脚本。
- WINDOWS_NON_CODING_SHELL_DISPATCH_GUIDANCE：说明独立只读查询可以同轮发出，修改状态或依赖前一步结果的命令要等待。

Shell 工具注册后的描述已经追加这两段内容。Shell 被拦消息中，也已经有独立查询可以分成多个调用、在同一响应发出的说明。

因此，本版不再新增 Parallel Dispatch 段，也不新增 format_tool_parallel_hint()。

不能因为修改了提示词，就把现有只读并行改成“一律一个调用一轮”；也不能把原有说明扩大成“所有不同文件都可以并行”。

### 3.3 核对工具描述，不等于重写所有工具描述

分析和验收时，需要检查模型最终收到的工具描述，而不只是配置界面里的简短介绍。

但这次实际修改保持克制：

- 与新提示无冲突的工具描述，原样保留。
- Shell 的共享限制和并行说明，原样保留。
- 不调整工具参数或注册方式。
- 不为了统一排版、翻译或缩短文字而重写全部函数说明。
- 如果发现必须改变工具选择或权限判定才能解决的问题，记录下来，不混入本次文案修改。

## 4. 主要改动一：在原位置把 Windows 提示写清楚

### 4.1 修改位置

文件：src/qwenpaw/app/chats/utils.py。

优先只调整 format_shell_atomic_hint() 中的少量说明。继续使用现有的生效条件：

- 当前运行在 Windows。
- 当前请求不是 Coding Mode。
- execute_shell_command 确实对模型可见。

不为加入这段文字改动 build_tool_usage_guidance() 的整体顺序，不增加新的工具选择步骤，也不重新安排 Skill 流程。

### 4.2 需要澄清的三个意思

| 要表达的意思 | 通俗解释 | 不代表什么 |
|---|---|---|
| 使用显示出来的默认 Shell | cmd 和 PowerShell 的写法不同，要按实际环境写命令 | 不自动切换 Shell，不更改执行后端 |
| 需要指定目录时，每次传入正确的 cwd | 上一次 cd 不会让下一次调用自动留在那个目录 | 不更改默认目录，也不把可选参数变成必填 |
| 失败后保持用户确认的目标 | 修正错误，不要为了成功而换一个文件或另一个输出位置 | 不允许绕过原有路径限制 |

“既有文件不受新建输出规则限制”仍然保留，但不能理解为该文件可以无视某个工具自身的限制。

例如，write_file 现有的第一挂载目录限制仍然存在。这里仅要求模型遵守工具原有说明，不修改该限制。

现有默认 cwd 已经适用时，仍可省略 cwd 参数。本次不要求每条命令都重复填写目录。

### 4.3 建议使用的短提示

下面给出英文候选，方便与当前代码中的英文说明保持一致。它是一小段说明，不是新的系统提示词。

~~~text
Use the displayed Default Shell. If a command needs a specific working
directory, pass it via cwd; an earlier cd does not carry over.
Each tool's existing path restrictions still apply. After a failure,
follow the specific error before retrying.
Keep the user's confirmed target; do not substitute another location
just to make the call succeed.
~~~

中文意思：

~~~text
按环境中显示的默认 Shell 执行命令。需要指定工作目录时传入 cwd，
不能认为上一次 cd 会对下一次调用继续生效。
每个工具原有的路径限制仍然有效。
失败后先看具体原因，修正原因后再试。
不要为了让调用成功，就换成另一个文件或另一个位置。
~~~

实际实施时，不要求整段照抄：

- 原位置已经表达清楚的句子，不重复添加。
- 优先补上缺少的部分，新增文字不超过上面这一小段。
- 保留原有规则的先后顺序和优先级。
- 不把这段说明复制到每个工具中。
- 不新增每一步都必须读取、验证或询问用户的要求。

### 4.4 原有示例怎样处理

现有有效示例优先保留，不因“精简”把某类限制的唯一示例删掉。

如确需替换容易引起误解的示例：

1. 替换后表达的仍是同一个限制。
2. 正确示例使用真实工具参数，不暗示默认目录里一定存在项目或脚本。
3. 错误示例明确标注原因，不让模型误以为可以照着执行。
4. 不增加新的并行示例或许可范围。
5. 不引导模型调用未开放的工具。

本版不要求重写全部示例。

## 5. 主要改动二：Shell 被拦后，把下一步说清楚

### 5.1 修改位置和范围

文件：src/qwenpaw/agents/tools/shell.py。

只修改 _guard_windows_non_coding_atomic_command() 已经命中的分支里的消息文字。

以下内容全部保留：

- requires_atomic_shell() 的生效判断。
- _detect_windows_shell_composition() 的识别结果。
- 哪些调用被拦、哪些调用继续执行。
- category、preferred_tool、state、metadata 等返回字段。
- 已有并行说明和条件分支。
- 原有 “Do not retry this combined command” 的要求。

不新增 _suggest_split_shell_calls()，不按符号自动生成一串工具调用。

### 5.2 为什么不自动拆命令

自动按符号切开，容易切出“看起来能执行，实际含义已变”的命令。

| 原命令的情况 | 机械拆分容易造成的问题 |
|---|---|
| cd /d 带空格路径，再运行程序 | 把 /d 当成目录的一部分 |
| 先设环境变量，再运行程序 | 第二个调用拿不到第一个调用设置的变量 |
| PowerShell 包装命令 | 去掉包装后，把 cmdlet 交给 cmd 执行 |
| 前一步成功才执行下一步 | 拆开后，无论前一步成功失败都继续 |
| 命令里包含复制或搜索 | 拆开后仍推荐被要求改用专用工具的 Shell 命令 |
| 混合多种组合符 | 拆出的某一段仍然违反原子限制 |

本版只解释应保留哪些条件，不假装已经完成准确的命令转换。

### 5.3 被拦消息需要讲清楚的内容

| 问题 | 应说明的下一步 |
|---|---|
| 多个独立步骤写在一条命令里 | 分别使用已有的合适工具，不把它们换个写法再次捆在一起 |
| 后一步依赖前一步 | 先看前一步结果，再决定是否执行后一步 |
| 使用 cd 改目录 | 在每个需要该目录的进程调用中传入正确 cwd |
| 需要环境变量 | 不假设上一个进程的设置会保留；按程序已有配置方式处理 |
| cmd / PowerShell 写法不一致 | 根据已显示的默认 Shell 修正，不能随意去掉解释器包装 |
| 管道或重定向 | 说明存在数据传递，不能简单切成无关调用 |
| 文件读写、复制或搜索 | 按当前可见工具及其现有限制处理 |

独立只读查询的并行建议继续使用原文，不改成所有操作都顺序执行。

### 5.4 条件依赖的补充文字示意

~~~text
Keep the original dependencies. Run a dependent step only after the
previous result shows that its prerequisite is satisfied.
Pass the required cwd on every call that needs it.
Do not assume shell variables survive between calls.
~~~

这只是对原有“根据结果决定是否继续”的解释，不增加新的执行限制。

### 5.5 管道和保存输出的说明要避免误导

现有错误消息会建议运行程序，再用 write_file 保存它返回的文字。

如保留这条建议，应补清它的适用条件：

- 返回的确实是文本。
- 结果完整，没有被截断。
- 通过工具保存返回文字，确实符合用户需要的文件内容。
- 输出路径符合已有规定。

不能把被截断的输出当作完整文件，也不能把二进制文件经模型转写保存。

程序已经支持合法的输出参数时，可以按现有规则使用。这里不新增允许的命令，也不放开重定向。

## 6. 可选补充：少数错误消息加一句具体建议

这部分不是扩大修改范围的理由。

先检查主要两处改动是否足够。只有某个常见错误目前明显缺少下一步说明，才补充对应文字。

### 6.1 候选位置

| 文件 | 候选分支 | 可补充的意思 |
|---|---|---|
| file_io.py | 写入异常 | 根据具体错误检查原目标，不要随意换目录 |
| file_io.py | 读取异常 | 确认已解析的路径及可读性，不猜另一个文件 |
| file_io.py | edit_file 读取异常 | 重新确认原文件能否读取，不扩大修改范围 |
| file_io.py | 追加异常 | 先核对文件当前内容，避免重复追加 |
| shell.py | 执行异常 | 按默认 Shell 检查具体语法或参数，不原样重复 |
| send_file.py | 交付异常 | 根据错误检查原文件，不声称已经发送成功 |

不是统一写“检查后重试”，也不是把所有异常都归因于路径错误。

### 6.2 错误消息的写法

建议保留原错误，后面加一到两句：

~~~text
原有错误内容

Next action: 针对这个错误的具体处理建议。
~~~

要求：

- 原异常原因不能被新文字遮住或删掉。
- 不改变 state、is_last、metadata 或任何返回结构。
- 新增建议只在 Windows 非 Coding 请求中显示。
- 其他模式返回的文字保持原样。
- 只增加选择提示文字所需的模式判断，不改允许、拒绝、审批、重试和执行判断。
- 不强制“再试一次”，尤其是可能已经部分追加、移动或交付的操作。
- 工具没有开放时，不生成那个工具的具体调用。
- 如果不能在很小的改动内做到范围准确，就暂不修改该候选分支。

### 6.3 三个例子

| 情况 | 合适的建议 | 不合适的建议 |
|---|---|---|
| 文件不存在 | 核对工具显示的实际路径，按已有发现规则确认来源 | 换个目录试试；猜另一个同名文件 |
| 修改文本未匹配 | 读取文件真实内容，核对匹配文字和范围 | 任意缩短 old_text，或直接整体覆盖 |
| 追加操作异常 | 先检查是否已有部分内容写入，再决定恢复 | 原样再追加一次 |

“修改文本未匹配”是正常错误返回，不一定发生在 except。只有在该分支确实需要补充说明时才修改，不为了覆盖所有错误而扩展为通用错误系统。

## 7. 并行行为怎样确保不变

### 7.1 原有说明原样保留

本次不修改 WINDOWS_NON_CODING_SHELL_DISPATCH_GUIDANCE 的文字。

Shell 工具描述和被拦消息中已经存在的并行说明，也不删减、不改义。

以下理解继续成立：

- 原来允许同轮发出的独立只读查询，仍然允许。
- 原来要求等待结果的命令，仍然等待。
- 原来依赖前一步结果的调用，不能提前猜参数。
- Skill 中已有的顺序和并行要求，仍然按原流程执行。

### 7.2 不新增许可，也不新增禁止

本次不加入：

- “只要目标文件不同就可以并行。”
- “所有读文件调用都必须并行。”
- “所有写文件调用都必须串行。”
- “只有下面列出的工具才准并行。”
- “所有工具都一轮只能调用一次。”

这些都会改变原有提示词含义，不属于本版。

文件工具、浏览器和其他工具原来怎样调度，继续由原有工具说明、流程和代码决定。本次不调整它们的并行范围。

### 7.3 实际调度代码不动

不修改工具分批、并发标记、执行队列、等待方式、超时或后台执行。

“把说明写清楚”不能顺便变成“给调度器新增一个判断”。

## 9. 已发现的问题及当前处理边界

保留这张表，是为了避免把“小范围修正”误说成“所有问题都已解决”。

| 已发现的问题 | 本版处理方式 | 不处理的原因 |
|---|---|---|
| 部分 Shell 执行失败却返回 SUCCESS | 公开状态保持原样；检查模型同时阅读状态和实际返回文本 | 模型检查不等于修复公开状态，其他调用方仍可能受影响 |
| send_file 异常返回 SUCCESS | 公开状态保持原样；检查模型同时阅读状态和实际返回文本 | 同上 |
| 网页失败建议 curl，而特定 Windows 路由又可能拦回网页工具 | 记录，不在本版重排网页恢复顺序 | 涉及多工具选择和不同模式，超出当前范围 |
| 已有总说明与 write_file 的单工具限制容易被混淆 | 提醒单工具现有限制仍有效 | 不改路径权限和覆盖行为 |
| 失败循环不能及时纠正 | 本次加入 FailureLoopGate，在下一次模型调用前提醒 | 不自动执行恢复操作，不替换已有停止限制 |
| 未开放工具出现在某些已有静态说明中 | 核对并记录；本版新增文字不得再引入 | 不为此重做工具注册或全部描述 |

| 文件操作之间可能存在并发依赖 | 保留原有行为 | 本次明确不调整并行 |

检查模型会同时分析工具名称、参数、状态和返回结果，不再通过固定错误前缀或失败次数决定是否提醒。成功状态不保证任务有进展，结果中出现 “Error” 也不必然表示本次工具执行失败。仍不能宣称识别所有内容错误或所有形式的循环。

独立检查会增加模型请求和等待时间，不承诺“零耗时”或具体准确率增幅。异常时跳过本次额外分析，不代表没有发生等待。

## 14. FailureLoopGate 只保留一种检查流程

### 14.1 当前执行顺序

~~~text
ReAct 推理决定要调用哪些工具
→ 工具按照原有方式执行，可以并行
→ 收集本批工具实际完成的调用和结果
→ 累计完成轮数达到配置间隔时，使用同一个模型检查当前任务的工具历史
→ 检查发现问题时，准备一条有长度上限的引导
→ 下一次 ReAct 推理结合最新实际情况，自行决定是否采纳
~~~

未达到间隔时，只收集并保存工具记录，直接进入下一次主推理。达到间隔后，检查使用异步接口，并等待检查结束，再开始下一次主推理。它不会在后台检查完后，把旧结论突然插到已经开始执行的新步骤中。

默认每累计完成 5 轮工具执行，发起一次检查。例如，完成第 5、10、15 轮后检查；配置为 1 就每轮检查。这里的一轮按照 ReAct 的工具执行轮次计算，同一轮并行执行多个工具只算一轮，不能把 5 个并行工具当成 5 轮。

只有完成了工具执行的轮次才计数。纯文字推理、没有新完成结果的再次准备，以及主请求的网络重试都不增加轮数。还有未完成调用时先不检查，不改变原有工具之间的并行关系。

间隔只决定何时检查，不缩小检查范围。每次仍分析当前任务截至当时的全部工具记录，按 Scroll 保留索引与近期原文，不是只查看最近 5 轮。

检查失败并耗尽本次重试后，也按已经尝试过一次检查处理，继续累计下一个间隔，避免下一轮立即再次请求。任务不足 5 轮就正常结束时，不为凑检查次数再额外执行一次；需要更及时的检查，可以减小间隔。

原有停止条件要求停止时，先按原有决定停止，不为了检查再发起模型请求。

### 14.2 检查哪些内容

只检查当前任务实际收到的工具记录，包括：

- 工具名称与完整调用参数。
- 调用编号、完成顺序编号和所属推理轮次。
- 最终状态、实际返回文本和结果附带字段。
- 是否转到后台、是否包含图片等非文本结果。
- 操作和结果的摘要值，便于旧记录经过 Scroll 后比较是否相同。

文本分批返回时，先收集各段，再在完成事件到达后形成一条记录。不会只保存工具名称，也不会只截取前面一小段错误文字。

这里的“完整”是运行时实际收到的内容。如果工具自身已经截断返回，检查器无法恢复没有收到的部分。图片等非文本内容保存原始返回；模型请求中仅给出类型、引用与摘要值，不把二进制编码当作已经理解的图片。需要视觉理解才能确定的进展，不能只根据摘要值判定。

检查请求还带有当前用户输入中最多 2,000 个字符的目标摘录，帮助判断操作是否必要。它只来自本次用户输入，不从整个 session 的历史中提取目标。

### 14.3 “当前任务”的边界

范围由当前 session 和本次 reply_id 共同确定。

同一 session 中，新的用户回复过程不会自动合并上一任务的工具记录。不同 session 的记录也不会混入。等待审批或外部执行后继续同一个 reply_id，可以恢复该范围内已经保存的调用和结果。

这不是自动理解出来的业务任务边界：一次回复里安排多个子任务，仍然会一起检查；同一业务任务跨两次新的用户输入，也不会自动合并。这一点需要和“整个 session 的全部历史”区分开。

### 14.4 独立提示词怎样组织

检查请求包含独立的系统提示、当前任务证据和本次检查要求。系统提示只说明怎样识别不必要的重复、相似尝试和跨工具循环，并要求返回判断依据和可选建议。

工具记录作为待分析数据发送，不提升为系统指令。工具返回中即使出现要求执行操作的文字，也不能变成检查器的指令。

不会引入以下内容：

- ReAct 系统提示词和历史思考文字。
- 自动记忆搜索结果。
- 同一 session 中其他任务的工具调用与结果。
- 原来本地规则模式的失败计数、规则分类和待发问题队列。

检查请求不开放业务工具，也不递归进入 ReAct。它只分析，不负责执行任务。

### 14.5 怎样避免把正常操作误判为循环

检查提示明确要求结合参数、目标、结果和前提是否变化进行判断：

| 情况 | 应怎样考虑 |
|---|---|
| 同一工具连续调用 | 不能只凭工具名称相同判断重复 |
| 不同工具交替调用 | 要看是否在围绕同一个问题反复绕圈 |
| 搜索成功但一直没有找到内容 | success 不等于原任务已经取得进展 |
| 分页读取、正常轮询、必要验证 | 不自动视为无效重复 |
| 修正参数或前提后重试 | 结合实际变化判断是否合理 |
| 同一批并行工具完成顺序不同 | 不把完成先后当作依赖关系 |
| Scroll 后细节不足 | 视为不确定，不强行判定有循环 |

代码只校验模型结果的格式和证据编号，不用本地相似度算法代替模型判断。

检查记录保存在当前工作目录的 failure_loop/history.db，与主 ReAct 的 history.db 分开。数据库内部继续按 session 和 reply_id 隔离。

未单独设置工作目录时，使用应用默认工作目录。直接构造检查器且没有提供保存路径时，使用临时目录，关闭时清理。

同一任务的记录中保存所属执行轮次，并单独保存上次已发起检查的位置。等待审批、外部执行或重建 Agent 后，继续累计该任务的间隔，不把已经检查过的轮次再计入下一次间隔。检查进度只用于调度，不作为工具证据加入提示词。

原始调用和结果先保存，再允许缩短发送给检查模型的窗口。检查器使用现有 Scroll 的归档、索引和整理流程，但拥有独立的上下文列表，不压缩或改写主 ReAct 的历史。

### 15.3 触发条件与 ReAct 一致

复用当前 ReAct 的 trigger_ratio、reserve_ratio 和自动压缩开关，并在每次检查模型请求之前计算：

~~~text
输入超过配置的 Scroll 触发比例，默认 0.8
或者
输入 token + 用户配置的最大输出 token > 用户配置的上下文长度
~~~

任一条件成立，就触发整理；整理后重新计算完整检查请求，满足总预算才发送。

例如，上下文为 131,072，最大输出为 65,536，检查输入为 65,537。虽然输入只占上下文的一半左右，还没到 0.8，但输入与最大输出相加超过上限，仍然必须先整理。

最大输出是用户配置值，不是本次预计回答多少字。不会为了让检查请求通过，擅自把它改小。引导长度上限也不会代替检查模型的最大输出配置。

计数使用同一模型的 count_tokens。当前 SDK 默认属于估算，不能说与服务端精确分词完全一致，因此这项保护不能承诺消除所有服务端超限错误。

### 15.4 单条特别大或压缩后仍然放不下

旧记录可以进入 Scroll 索引，保留编号、工具、操作与结果摘要值及短摘录；近期记录尽量保留原文。

最新一条结果或参数本身特别大时，只有确认原始内容已经安全保存，才改成头尾摘录和摘要值。仍然放不下，或原文保存失败，就跳过本次额外检查，不发送已知超出预算的请求，也不生成假装已经完成检查的结论。

关闭自动压缩时，检查器不会擅自开启 Scroll 整理。检查请求超预算，就跳过这次检查；主 ReAct 仍然执行自己的预算保护。

“检查当前任务全部工具历史”表示记录范围完整，不表示每次都重新发送全部原文。旧原文保存在独立记录库，当前窗口使用索引和近期原文。检查模型没有回查工具，所以经过整理后证据不足的情况，应当承认不确定。

## 16. 引导只供下一次推理参考，不持续堆积

### 16.1 什么情况下加入引导

模型返回是否发现问题，以及问题类型、原因、建议和证据编号。问题类型限定为重复、相似执行或循环，每项至少引用两个不同且实际存在的完成编号，最多三项。

没有发现问题、格式错误、证据编号不存在或证据不足时，不把该结论加入主推理。检查失败后也不会切换到另一套本地规则生成建议。

有问题时，引导明确包含以下意思：

~~~text
这是截至第 N 条工具完成记录的检查建议，可能有误判或已经过时。
请根据最新实际结果，自行决定是否采纳。
如果问题已纠正，或重复操作有充分理由，可以忽略本次建议。
不要因此重复已经完成的工作。
现有权限、确认目标、工具限制和并行规则仍然适用。
~~~

引导不是停止命令，也不是自动重试、换目标或突破限制的许可。

### 16.2 引导有长度限制，且不写入历史

每次主模型请求最多附加一条临时引导，内含最多三项发现。整条消息的固定说明、证据和建议合计，默认不得超过 512 token。

`max-hint-tokens` 就是这条临时引导的长度上限。token 是模型计算长度的单位，不直接等于中文字数。这个参数用来避免检查建议本身过长，挤占主 ReAct 推理所需的上下文空间。

| 内容 | 长度由谁决定 |
|---|---|
| 检查模型要读取的提示与工具历史 | 与 ReAct 一致的上下文预算，必要时通过独立 Scroll 整理 |
| 检查模型允许生成的最大输出 | 复用 ReAct 的最大输出配置，不改成 512 |
| 最后临时附加给 ReAct 的引导 | max-hint-tokens，默认 512 |

它不控制检查频率，也不把历史工具结果截成 512 token。例如，间隔设为 5、引导上限设为 512，表示每完成 5 轮检查一次；发现问题后，给下一次推理的完整引导最多占 512 token。

放不下时减少完整条目，不把句子截成半条指令。连一项完整引导都放不下，就省略本次引导。说明“由模型根据实际情况自行决定是否采纳”的文字会随第一项保留，不为了节省长度而删掉。

引导不追加到 state.context，不随长任务不断积累到历史。下一次推理没有新检查结论，就不自动重放上一轮引导。主请求的网络重试复用同一份引导；切换备用模型时，按备用模型重新计算其长度和请求预算。

主 ReAct 的完整预算检查仍在临时引导之后执行。如果只有引导导致超限，而省略后原请求能放下，就省略引导。原请求自己仍然超限时，按主流程原有规则处理。

### 16.3 避免发送过期引导

检查前记录当前 session、reply_id、推理轮次和完成记录数量。检查结束以及实际附加引导前，再次核对这些状态。

如果已经切换任务、进入其他推理轮次、新增完成结果，或者又出现了未完成调用，本次旧引导就不发送。不会等主模型已经选好下一批工具后，再补送上一批的判断。

### 16.4 检查器异常时怎样处理

普通异常会被记录，并跳过本次额外检查或引导：

| 异常 | 处理 |
|---|---|
| 模型请求失败、超时 | 按共享配置重试或使用备用模型；仍失败则跳过引导 |
| 返回不是有效 JSON，或引用了不存在的证据 | 不注入该结论 |
| 检查上下文无法压缩到预算以内 | 跳过检查，不发送已知超预算请求 |
| 工具记录采集或保存抛出异常 | 停用本次回复的额外检查，原工具事件继续传递 |
| 引导计数异常或引导放不下 | 省略引导，继续主请求 |

这表示普通检查异常不会直接打断主流程，不表示完全没有影响。检查会等待完成，共享的超时、重试和备用模型尝试可能增加耗时；当前没有另加独立的检查总超时。

用户取消和停止信号仍然生效，不作为普通异常吞掉。主流程自己的权限限制、停止条件和预算错误也不被掩盖。

## 17. 配置、删除范围与验证

### 17.1 三个环境变量各自负责什么

| 环境变量 | 默认值 | 用途 |
|---|---:|---|
| QWENPAW_FAILURE_LOOP_ENABLED | 0 | 是否在 Windows 非 Coding 请求中装配检查器 |
| QWENPAW_FAILURE_LOOP_CHECK_INTERVAL | 5 | 每累计完成多少轮工具执行，发起一次模型检查；必须为正整数 |
| QWENPAW_FAILURE_LOOP_MAX_HINT_TOKENS | 512 | 最后附加给主推理的整条引导长度上限 |

启用方式：

~~~powershell
$env:QWENPAW_FAILURE_LOOP_ENABLED = '1'
$env:QWENPAW_FAILURE_LOOP_CHECK_INTERVAL = '5'
$env:QWENPAW_FAILURE_LOOP_MAX_HINT_TOKENS = '512'
python main.py
~~~

也可以使用：

~~~powershell
python main.py --failure-loop-enabled 1 --failure-loop-check-interval 5 --failure-loop-max-hint-tokens 512
~~~

命令行显式值覆盖环境变量；未传参数时保留环境变量。总开关默认关闭，本次不改变现有启用范围。已经运行的服务需要重启，新配置和代码才会生效。

检查间隔和引导长度都必须为正整数。环境变量无效时记录警告，并分别回退到默认 5 和 512。间隔不是旧的失败次数阈值：成功和失败的工具执行轮次都会计入，到期后由模型判断是否存在问题。
