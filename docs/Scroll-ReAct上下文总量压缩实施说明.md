# Scroll：ReAct 上下文总量检查与自动压缩

> 更新日期：2026-10-14。已实施并完成本地回归测试。
>
> 本次按用户确认的范围修改：保留 0.8，在每次 ReAct 调用模型前检查完整输入加用户配置的最大输出。没有增加安全余量，没有自动缩小最大输出，也没有增加服务端错误恢复重试。

## 1. 本次解决的问题

只根据输入是否达到上下文的 80% 决定压缩，无法覆盖“输入没有达到 80%，但加上最大输出后已经超限”的情况。

截图中的数值是：

| 项目 | token 数量 |
|---|---:|
| 配置的上下文长度 C | 131,072 |
| 配置的最大输出 O | 65,536 |
| 本次完整输入 P | 至少 65,537 |
| 输入加最大输出 | 至少 131,073 |

这次输入约占上下文的 50%，不会达到 80%，但总量已经超出上限。

## 2. 现在的判断规则

~~~text
P = 本次 ReAct 准备发送的完整输入 token 数
O = 当前模型配置的最大输出 token 数
C = 当前模型配置的上下文长度

常规触发：P >= C × 0.8
预算触发：P + O > C

任意一个条件成立，进入 Scroll 压缩。
预算压缩后的输入必须满足：P <= C - O。
~~~

恰好等于上限时允许发送。例如 P 为 65,536，O 为 65,536，C 为 131,072，总量相等，不因总量检查触发压缩。P 为 65,537 时则触发。

0.8 沿用原有配置值，没有改成另一种比例。用户配置的最大输出不会为凑长度而被调小。

## 3. 什么时候检查，检查哪些内容

本次不是只在用户发消息时检查，而是在 ReAct 每次准备调用模型时检查。工具执行后，下一次推理也会重新检查。

整体顺序如下：

~~~text
准备对话和工具结果
→ 原有 Scroll 检查，增加总量触发条件
→ 运行时加入记忆、继续提示、失败纠正等内容
→ 最后的模型调用中间件检查实际完整请求
→ 必要时按 C - O 整理
→ 重建请求，重新计数
→ 满足预算后才调用模型
~~~

完整输入包括系统提示、摘要、Scroll 索引、历史、当前请求、工具参数说明、工具结果及本次追加的记忆和提醒。

用户消息已经在请求中时，不会再额外加一遍。发送前检查直接使用本次的 messages 和 tools，也不会只统计 agent.state.context 而漏掉外部追加内容。

## 4. 配置如何取得

构建当前模型时，从已有模型配置保存本次预算：

- 用户明确配置的上下文长度，优先使用原值。即使配置值刚好是 131,072，也不会因此被静态模型目录覆盖。
- 最大输出使用当前模型已有的生成参数配置，兼容 max_tokens、max_completion_tokens 和 max_output_tokens，不把别名相加。
- 没有明确设置上下文长度时，沿用现有模型窗口解析结果。
- 模型有多层包装时，通过同一个预算对象传递，避免读到包装层默认值。
- 备用模型实际被调用时，按它自己的配置重新核算。

没有新增环境变量或界面配置。临时注入、自定义模型需要提供有效的上下文长度和最大输出，或者提供预算对象；无法取得这两个值时，明确提示配置不完整，不猜一个输出值。

## 5. 压缩如何执行

Scroll 新增 compress_to_budget 入口，复用已有压缩流程，不复制另一套历史管理：

1. 先确认需要移出的内容已经安全保存。
2. 移出较旧历史，保留当前任务。
3. 缩减 Scroll 索引。
4. 必要时折叠当前任务中已经完成的较旧工具结果。
5. 重新构建完整请求并计数。

入口和最后折叠步骤都考虑 C - O，不会再因为“输入还未达到 80%”而跳过预算处理。

原有保留比例仍是整理目标；当前用户请求、最新工具结果和工具调用与结果的对应关系继续受到保护。不会为了过检查随意截断这些内容。

如果历史保存失败、固定提示过大、当前请求过大，或者已经没有可以安全缩减的内容，整理后仍超限就返回明确错误，不发送该次模型请求。C - O 小于等于零且请求超限时，直接说明没有输入空间。

自动压缩关闭时，不擅自开启压缩。对于仍然超限的请求，本地说明原因并停止发送。

## 6. 怎样保留本次额外内容

压缩后会保留本次实际请求中的系统提示、摘要前缀、工具说明和额外消息，再放入 Scroll 整理后的对话。不重新执行记忆检索，不重复加入用户消息，也不重新执行工具。

如果插件把对话消息改写、交错插入到无法安全重建的程度，而且请求确实超限，就明确拒绝发送，避免为了缩短长度而丢弃或重排插件内容。没有超限的请求直接沿原流程执行。

模型已有重试流程可能再次传入旧消息列表。本次会在同一回复、同一次推理、上下文未改变且请求来源匹配时，复用已经整理的请求，再做预算检查，防止重试时遗漏记忆或重新带回旧历史。新推理、不同附加内容或上下文变化会使这份记录失效。

对于内容和配置完全相同、已经确认无法满足预算的请求，既有 SDK 重试不会重复执行预算压缩。记录只保存请求标识和错误信息，不重复保存完整历史或异常调用栈。

没有改变模型重试次数、权限、工具并行、FailureLoopGate 或原有停止条件。新增操作通过 await 在模型调用前完成，不在后台检查尚未结束时先发送请求。

## 7. 修改位置

| 文件 | 作用 |
|---|---|
| src/qwenpaw/agents/context/request_budget.py | 保存 C、O，计算 C - O，读取模型预算，保存可安全重建的请求前后附加部分 |
| src/qwenpaw/agents/context/budget_middleware.py | 最终总量检查、预算整理、重新计数、阻止仍超限请求，并保留同次推理重试内容 |
| src/qwenpaw/agents/context/scroll/manager.py | 复用原有 Scroll 流程，增加预算入口，调整触发和折叠判断 |
| src/qwenpaw/agents/model_factory.py | 从当前选中模型的已有配置传入预算 |
| src/qwenpaw/runtime/builder.py | 仅在 Scroll 实际启用时，把预算检查放在模型调用中间件的最后 |
| src/qwenpaw/agents/react_agent.py | 自动压缩关闭时保留该选择，不在常规 Scroll 调用中提前压缩 |
| tests/test_request_budget.py | 预算规则、真实 Scroll、真实 ReAct、记忆、工具结果和重试测试 |

第一版仅接入实际启用 Scroll 的 ReAct 路径。原生上下文策略及直接调用模型的辅助任务，没有新增这项发送前中间件。没有修改第三方 AgentScope 安装文件，也没有新增依赖。
