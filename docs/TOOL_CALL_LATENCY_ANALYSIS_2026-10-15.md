# write_file / list_skills 慢调用分析

分析日期：2026-10-15。对象为对话中的 Agent 工具调用，不是技能管理页 REST 接口。本次只分析日志、调用链及只读采样，没有修改执行代码、提示词、权限或模型配置。

## 结论

当前样本的主要等待发生在主模型推理和流式输出阶段，发生在工具函数实际执行之前。不能把一轮里出现 write_file/list_skills，就把该轮全部耗时归到文件写入或技能列表函数。

与此同时，list_skills 确实存在不必要的全量工作：分页之前读取全部技能正文和引用/脚本目录树。当前小技能池采样约 0.13 秒，值得做轻量化，但不是此样本几十秒乃至上百秒等待的主要来源。

## write_file 调用链

当前源码 `agents/tools/file_io.py`：

```text
模型生成完整 tool_call 参数
→ SDK 权限检查和调用准备
→ PolicyGuardedTool 包装器打印入参
→ write_file
→ 默认根/首挂载/只读目录等路径检查
→ 创建缺失父目录
→ aiofiles.open + write + close
→ ToolChunk 结果
```

write_file 本体没有再次调用模型，也不走 Shell semantic guard。当前样本中，其权限记录、包装器进入和下一模型轮开始都落在同一秒，未出现几十秒的执行窗口；纯路径检查、线程池等待和写盘各自耗时尚无单独日志，不能给出它们的精确毫秒值。

110 秒那轮试图向 session scratch 的绝对路径写 make_mask.py，但本请求首个外部可写挂载为 `C:/Users/Best0/Desktop/x8`，因此正确返回 DENIED。下一轮改为相对路径后，同样的 672 字符写入成功。这里额外增加的是路径错误后的模型修正往返，不应通过放宽写入边界消除拒绝。

该会话五次 write_file 为四次成功、一次路径拒绝，不是五次全部成功，也没有证据表明被拒绝那次发生了写盘超时。

## list_skills 调用链与采样

当前源码 `agents/tools/pool_skills.py`：

```text
获取主技能池和额外技能根
→ 按根优先级遍历全部子目录，排序、去重
→ 为每个候选调用 read_skill_from_dir
→ 读取完整 SKILL.md、解析 frontmatter
→ 递归构造 references / scripts 目录树
→ 构造完整 SkillInfo
→ 全量收集后，才按 offset / limit 切页
→ 仅输出名称、描述、目录
```

重工作来自 `skill_system/store.py::read_skill_from_dir`：列表最终不使用正文、目录树和完整详情对象，却为所有技能构造了这些数据。get_skill_count 也复用了这个重读取路径，所以“先 count 再 list”不是当前实现里的轻量优化。

本次用当前源码中的扫描、解析、分页和组装函数，对日志返回的主技能池进行了三次只读采样：

| 次数 | 核心处理耗时 | 完整读取技能数 | 返回页 |
| --- | ---: | ---: | --- |
| 1 | 137.597 毫秒 | 22 | 前 20 项，共 22 项 |
| 2 | 129.079 毫秒 | 22 | 前 20 项，共 22 项 |
| 3 | 127.411 毫秒 | 22 | 前 20 项，共 22 项 |

采样范围不含主模型、权限、HTTP、实际运行时配置读取和额外技能根；不能冒充线上完整接口计时。其规模和返回头与当前日志中的主池一致。它说明当前主池扫描是百毫秒量级，未支持扫描花了几十秒的判断。

由于先全量收集再切页，调小 limit 主要减少返回文本，不会等比例减少扫描工作。函数虽为 async def，但遍历、读取和解析部分是同步操作；async 声明本身不会将其变成非阻塞文件 I/O。技能池或目录树变大时，这仍是可扩展性问题。

## 门禁、提示词和显示状态

- 两个样本会话的 FailureLoopGate 日志均为 `enabled=False reason=disabled_by_config`，不是本次慢调用的来源。
- 长任务的 12 次 Shell 审查均记录 `thinking_mode=disabled`，累计约 36.014 秒。其中一次 split_instruction，其余 allow_shell；write_file/list_skills 本体不调用这套审查。
- Shell thinking 开关不控制主模型 thinking，当前主模型仍产生了大量 thinking 输出。
- 同区间 10 次 Bash 审批均有自动批准记录，不能把它们描述成用户手动等待审批造成的几分钟延迟。
- 样本区间未找到明确的模型重试、429 或 502 记录；这不等于排除了网络/服务等待。
- 当前运行工作区的 AGENTS.md / SOUL.md 与源码字节一致，不能把这两份 Markdown 的旧版本未同步当作原因。该检查没有证明所有可执行文件中的代码和常量均与源码一致。
- SDK 在模型流中首次出现工具调用时就发 ToolCallStartEvent，参数随后继续流式传输；实际执行在模型轮结束后。现有 V1 卡片无结果时统一为 calling，所以显示工具名/调用中不等于文件函数已经开始写盘。不能将整个 calling 区间当纯执行计时。

## 后续优化优先级

1. **先拆清阶段。** 增加每个 call ID 的参数接收结束、权限开始/结束、函数进入/退出，以及 list 的扫描/解析和 write 的路径/写盘耗时；只记录阶段、状态和大小，不重复打印正文。前端区分“准备参数、等待授权、执行中、已返回”。
2. **主模型阶段收益最大。** 按用户后续澄清，在每个任务开始实际调用 list_agents 和 list_skills；二者独立，可同轮调用，不限定平台、模式、顺序或固定分页大小。同一任务跨用户消息、ReAct 和 Scroll 复用有效结果，详情缺失先取回原结果。若要进一步优化，应单独评估主模型的推理强度和任务执行轮数；不要把现有 Shell thinking 开关当成全局开关，也不因本分析直接改变本地模型策略。
3. **减少同一规则下的失败返工。** 保持首挂载与相对路径规则，避免反复生成 scratch 绝对输出；优先使用 Skill 已有且满足任务的执行路径，证据足够后交付，避免无新证据的多轮重复尝试。
4. **再轻量化列表实现。** 专用列表投影只取得名称、描述、目录及有效性，不为列表递归引用/脚本树或构造完整详情。排序、跨根优先级、去重、总数、分页、错误处理须保留。任务启动发现不可省略；如考虑内部缓存，必须另行定义可靠失效，不以其他任务目录替代本任务的启动调用。

优化列表的百毫秒处理可以改善后台负载，但在该样本中，即使将其降到零，也无法解决主模型阶段的十几分钟等待。应先用分段数据判断收益，而非先增加工具并发数或削弱门禁。
